One change produced nearly all of that: replacing the per-node Python loop with a NumPy array operation. No threading, no multiprocessing, no compiled extension. The algorithm is unchanged and the maps it produces are the same. Detail in Finding 02.

Starting point

The code under review

Worth saying up front: this is not bad code. It is a faithful, readable transcription of the algorithm straight out of the paper, and it produces a correct map. Every problem below comes from the gap between working once and being run, changed and trusted by other people.

Findings, ranked by what I would fix first

Top five recommendations

01

The input dimensionality is hardcoded to 3

Correctness Silent failure

The weight grid is built as (width, height, 3). That 3 is not a property of the map, it is the dimensionality of the input data, and it only happens to be right because the example feeds in RGB colours.

Why this is first

The reason to reach for a SOM at all is high-dimensional data: a 50-field customer profile, a sensor vector, a document embedding. This implementation handles exactly one case, the 3-dimensional one, which is the case you least need a SOM for. Pass 50-dimensional data and it raises a broadcasting error from inside the training loop, with nothing pointing at the real cause.

Before
weights = np.random.random((width, height, 3))
After
# n_dimensions comes from config, validated
# against the data before training starts
weights = utils.initialise_weights(
    width, height, n_dimensions
)

Paired with an explicit check, so a mismatch fails immediately with a message that says what is wrong:

02

Every node is updated one at a time, in Python

Performance ~83× on the large run

The inner for x / for y pair walks the grid node by node. NumPy is already imported and already in use, but the grid work is being done by the Python interpreter rather than by NumPy.

1000 iterations × 10 input vectors × (100 × 100 nodes) = 100,000,000 interpreter-level loop passes
The insight

Influence and the weight update are the same arithmetic applied independently to every node. Nothing in the inner loop depends on the result of the previous node, so it never needed to be a loop. Broadcasting the grid coordinates against the BMU position computes the whole influence field in one array operation.

Before: per-node Python
for x in range(width):
    for y in range(height):
        di = np.sqrt(((x - bmu_x) ** 2)
                     + ((y - bmu_y) ** 2))
        θt = np.exp(-(di ** 2)
                    / (2*(σt ** 2)))
        weights[x, y] += αt * θt * (vt - weights[x, y])
After: whole grid at once
# (width,1) against (1,height) broadcasts
# to the full (width,height) grid
distance_squared = (
    (x_coords[:, np.newaxis] - bmu_x) ** 2
    + (y_coords[np.newaxis, :] - bmu_y) ** 2
)
influence = np.exp(-distance_squared
                   / (2 * sigma_t ** 2))

weights += (alpha_t * influence)[:, :, np.newaxis] \
           * (input_vector - weights)

Two smaller wins that came with it

  • No square root. The original takes sqrt to get the distance, then immediately squares it again inside the Gaussian. Keeping the distance squared throughout removes a wasted operation per node. The same reasoning applies to the BMU search, where squared distance is enough to find the minimum.
  • Grid coordinates built once. np.arange(width) and np.arange(height) never change during training, so they are computed once per run rather than rebuilt inside the loop.
What I considered and rejected

Threading was the first idea, since node updates look embarrassingly parallel. It is the wrong tool here: the GIL blocks any gain on pure Python arithmetic, and the vectorised version already pushes the work into NumPy's C loops, which release the GIL anyway. Vectorising first meant the concurrency question never needed answering.

03

Greek variable names that cannot be typed

Maintainability Collaboration

σ0, αt, λ and θt are valid Python 3 identifiers, and they match the notation in the paper exactly. That is the argument for them. The argument against is practical: a developer cannot type them without a character picker, cannot grep for them reliably, and cannot say them out loud in a review.

The underlying issue

Matching the paper's notation is a real goal, it just belongs in the docstring rather than in the identifiers. Naming sigma_0 in code and explaining that it is the paper's σ₀ in a comment gives you both: the code stays typeable, and the link to the source maths stays explicit.

Before
σ0 = max(width, height) / 2
λ = n_max_iterations / np.log(σ0)
σt = σ0 * np.exp(-t/λ)
αt = α0 * np.exp(-t/λ)
After
sigma_0 = utils.initial_radius(width, height)
time_constant = utils.decay_constant(
    n_max_iterations, sigma_0
)
sigma_t = utils.exponential_decay(
    sigma_0, iteration, time_constant
)
alpha_t = utils.exponential_decay(
    alpha_0, iteration, time_constant
)

Naming the decay as a shared function also surfaces something the original hides: the radius and the learning rate are not just similar, they run on one identical schedule. That is a design decision worth being able to see, and worth being able to change in one place.

The same pass replaced vt with input_vector, di with distance_squared, and added docstrings to every function. Names now say what a thing is rather than which letter it was in the paper.

04

Constants are buried in the function body

Operability Reproducibility

The learning rate 0.1 sits inside train(). Grid sizes, iteration counts and output filenames sit inside __main__. Changing any of them means editing Python, which means a code change, a review and a commit for what is really a parameter sweep.

Why it matters beyond tidiness

Once tuning requires editing source, two things follow. Nobody without repo access can run an experiment, and there is no record of which settings produced which output. Moving the values into a config file makes the run parameters a versioned artefact that can sit next to the result.

The config is read through load_config(), which resolves the path relative to the module rather than the working directory, refuses a missing or empty file, uses yaml.safe_load rather than load, and validates every key before returning. A typo in the config fails at startup with the key name, not halfway through a six-minute run.

05

Nothing checks the inputs, reports progress, or proves the output

Production readiness Observability

Three gaps that are invisible while the code works and expensive the moment it does not.

No guardrails

Every argument is trusted. An empty array, a NaN, a zero-width grid or a learning rate of 5 all get through. Some raise a confusing NumPy error deep inside the loop; worse, some produce a plausible-looking map that is quietly wrong. One case is subtle enough to be worth calling out: λ = n_iterations / log(σ0) divides by log(σ0), so a 2×2 grid makes σ0 = 1, log(1) = 0, and the decay constant becomes infinite. The fix validates that the larger grid side is at least 3 nodes, and explains why in a comment.

No logging

The 1000-iteration run took nearly six minutes and printed nothing. There was no way to tell it apart from a hang, and no way to see the decay schedule going wrong until the image came out. Training now logs its configuration on entry, then progress with the live sigma and alpha values, so a bad schedule is visible in the first few lines rather than at the end.

No tests

There is no way to change this code with confidence, because there is nothing that tells you when you have broken it. The properties are easy to assert: influence is exactly 1.0 at the BMU and falls with distance; a returned grid has shape (width, height, n_dimensions); decay is monotonically decreasing; a known input moves its BMU closer to itself. Post-training checks are in place (shape and finiteness are asserted before the weights are returned or saved), and the validation layer is the part a test suite would exercise first.

Being straight about status: the validation and logging described above are implemented. The unit tests are specified but not yet written. That is the top item on the list at the end of this page rather than something already done.

Question three

How I approached productionising it

Structure first, then correctness, then speed. Restructuring before optimising meant the performance work landed in one small function with a clear contract, rather than being threaded through a 20-line block doing five jobs at once.

Before

kohonen.py   ← everything

After

prod_code/
├── kohonen_som.py     training loop
├── utils.py           config, maths, i/o
├── validations.py      pre/post checks
├── config.yaml         all constants
├── requirements.txt    pinned deps
├── README.md           what and why
└── results/           generated maps

The order I worked in

  • Repo structure and a README, so the shape of the thing is legible before anything moves.
  • Pinned requirements and a virtual environment, so a run is reproducible on another machine.
  • Benchmark the original, before touching it. Without the 5m 54s baseline there is no way to claim an improvement later.
  • Naming, docstrings and module boundaries, pulling the maths into named single-purpose functions.
  • Constants into config, with validation on load.
  • Logging and error handling, including a top-level handler that logs the full traceback.
  • Then, and only then, performance. By this point the update step was one function, so vectorising it was a contained change with an obvious before and after.

The maps below are the output of the vectorised implementation. Similar colours sit next to each other, which is the topology-preserving property the algorithm exists to produce, and it is also the quickest visual check that a change has not broken anything.

Honest status

What I would do next

The review asked for recommendations rather than a finished implementation, so this is where I stopped and what I would pick up next.

Next

Unit tests

The properties are already specified in Finding 05. The validation layer and the maths helpers are the natural first targets, since both are pure functions.

Next

Seeded runs

Weight initialisation and input generation both call np.random unseeded, so no two runs match. A seed in the config would make results reproducible and make tests deterministic.

Next

Type hints

Docstrings document the shapes and types; hints would let a checker enforce them.

Further out

Batch the BMU search

The BMU is still found one input vector at a time. For a large input set that loop becomes the next bottleneck, and the same broadcasting argument applies to it.

Further out

Persist the trained map

The weights are saved as a PNG and otherwise discarded. A trained SOM is a model: it should be serialisable, and loadable to place new points without retraining.

Further out

CI and linting

Tests and a linter on every push, so the guardrails stay enforced rather than depending on the person who last touched it.
